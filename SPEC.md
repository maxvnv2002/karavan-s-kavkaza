# Караван с Кавказа

## Текущий этап

Рабочая папка была пустой. Проект создан на Next.js 16 App Router, React 19 и TypeScript. Эталон — публичные и административные экраны UX-версии Figma. Каталог, контакты и сроки взяты из макета. Правовые тексты требуют заполнения. Форма и панель управления записывают заявки и их статусы в браузере. [Макет главной](https://www.figma.com/design/nPD9KHYFLNbuUmYArYCWE0/Untitled?node-id=52-1308)

| ID | Маршрут или интерфейс | Критерий приёмки |
| --- | --- | --- |
| R1 | `/` | Главная соответствует мобильному и десктопному макетам. Каталог, производство, контакты и форма доступны с клавиатуры. |
| R2 | `/catalog` | Поиск по названию и артикулу, тип цены, категория, подкатегория, дата и сортировка работают. Прямой URL с параметрами открывает отфильтрованный каталог. Серверная сборка применяет фильтры при рендеринге HTML, сборка для GitHub Pages — в браузере. |
| R3 | `/catalog/[batch]` | Ссылка ведёт на конкретную партию. Для крылышек можно перейти к другой партии. Неизвестная партия возвращает 404. |
| R4 | `/production`, `/contacts`, `/privacy` | Страницы доступны по прямым URL. Статусы отсутствующих документов отображаются средствами интерфейса. |
| R5 | Форма малого опта | Можно выбрать товары и объёмы, добавить и убрать позиции. Отправка требует корректный телефон, объёмы и обязательное согласие. Согласие на рассылку отдельное и необязательное. |
| R6 | Политика поверх формы | Возврат из политики сохраняет поля и согласия. Escape возвращает из политики к форме или закрывает форму, если политика закрыта. |
| R7 | Cookies | Выбор сохраняется локально. Настройки из подвала позволяют изменить выбор. Счётчики не подключены. |
| R8 | Рендеринг и адаптивность | Публичные маршруты поставляют серверный HTML и метаданные. При заданном `SITE_URL` публикуется карта сайта. Страницы панели управления содержат указание поисковым роботам не индексировать их. |
| R9 | Сохранение заявки в браузере | Покупатель видит подтверждение, номер заявки и кнопку возврата к покупкам. Заявка доступна в панели управления в том же профиле браузера. После перезагрузки сохраняются позиции, телефон, статус и версия согласия. |
| R10 | `/admin/requests` | Заявки можно искать, фильтровать, брать в работу и закрывать. Счётчик учитывает новые и активные заявки. Закрытые доступны в истории. |
| R11 | Хранилище браузера | Новый профиль начинает с четырёх тестовых заявок. При недоступном хранилище форма показывает ошибку и сохраняет текущий черновик. |

Десктопная компоновка каталога и товара адаптирована из мобильных экранов. Панель управления использует общую навигацию и счётчик открытых заявок. Публичные страницы продолжают поставлять серверный HTML с исходными данными. Изменения в панели управления сохраняются в браузере.

| ID | Маршрут | Критерий приёмки |
| --- | --- | --- |
| R12 | `/admin/catalog` | Поиск и фильтры списка позиций, изменение остатка, управление забоями, категориями и ступенями скидок. |
| R13 | `/admin/catalog/products?id=…` | Редактор отделяет общие данные товара от полей партии, показывает результат расчёта цены и даёт добавить партию в другой забой. Разрушающие операции требуют подтверждения. |
| R14 | `/admin/catalog/slaughters?id=…` | Адаптивный экран забоя по мобильному макету: параметризация, список партий и компактное редактирование выбранной позиции. |
| R15 | `/admin/content` | Тексты и контакты сохраняются отдельно от черновика производства. Сведения можно отметить для публикации после проверки и подтверждения. |
| R16 | `/admin/company` | Реквизиты, файлы для оптовиков, политика, согласия и настройки аналитики редактируются независимо. |
| R17 | `/admin/stores` | Создание, редактирование, предпросмотр, отметка для публикации и удаление розничной точки. Адрес самовывоза задаётся отдельно. |

## Запуск

Требуется Node.js 22.13+ в ветке 22 либо Node.js 24+. Установка и локальный запуск выполняются командами `npm ci` и `npm run dev`. Для проверки production-режима используются `npm run build` и `npm run start`. `SITE_URL` задаётся абсолютным URL при сборке для метаданных и sitemap.

### GitHub Pages

Для локальной статической сборки запустите `BUILD_FOR_PAGES=true npm run build`. Папка `out` содержит файлы для публикации по пути `/karavan-s-kavkaza/`. Workflow [Deploy to GitHub Pages](.github/workflows/pages.yml) получает путь и URL из настроек Pages и публикует сборку из `main`. В репозитории выберите **Settings → Pages → Source → GitHub Actions**.

Заявки и изменения в админке сохраняются в браузере, поэтому опубликованная сборка подходит для демонстрации с тестовыми данными.

## Данные и граница интеграции

- `src/features/catalog/data.ts` задаёт товары и партии. Товар описывает ассортимент и минимальный объём малого опта. Цена, скидка, остаток и срок хранения относятся к партии. Каталог публично показывает разные партии одного товара. В заявке покупатель выбирает товар, а менеджер подтверждает партию и итоговые условия.
- `src/features/wholesale/request.ts` содержит типы, нормализацию телефона и проверку позиций. Одна заявка содержит от одной позиции до числа доступных товаров. Один товар можно выбрать один раз. Количество задаётся в килограммах от минимума товара до 10 000 кг. Телефон приводится к `+7XXXXXXXXXX`.
- `src/features/wholesale/request-store.ts` предоставляет `createRequest`, `useRequests` и `changeRequestStatus`. Локальное хранилище `karavan.wholesale.v1` сохраняет заявки как массив. Индикатор отображает `new + active`. Допустимые переходы статусов: `new → active → closed` и `new → closed`. Повторный переход закрытой заявки отклоняется. Синхронизация вкладок использует события хранилища, запись сериализуется через Web Locks, где они доступны.
- Форма передаёт в адаптер ID товаров, объёмы, телефон и два флага согласия. В сохранённой записи есть версия обязательного согласия, отдельный флаг рассылки, время создания, номер и статус. Для проверки используют тестовые номера. Данные существуют в текущем браузере, уведомления менеджерам отсутствуют.

## Клиентская модель админки

- `src/app/admin/layout.tsx` задаёт общий каркас и закрывает дочерние страницы от индексации. Счётчик читает то же хранилище, что раздел заявок. `/admin` по-прежнему ведёт к заявкам, забой открывается из каталога.
- `catalog` хранит справочники товаров и категорий, забои, товарные позиции и ступени скидок. Позиция ссылается на товар и забой. В одном забое допускается одна позиция с данным товаром. Артикул уникален без учёта регистра. Удаление забоя удаляет его позиции, удаление товара — все его позиции. Справочник товаров сохраняет товар после удаления одной партии. Для удаления категории нужно перенести товары и дочерние категории.
- Позиция содержит базовые цены, минимальные объёмы, остаток, срок, режим хранения и переключатель видимости. Цена рассчитывается по последней активной ступени возраста, ручная скидка забоя имеет приоритет, а позиция может отключить скидку. Цена округляется до рубля, возраст считается полными сутками. Для расчёта в предпросмотре используется 23.11.2026, 08:00, UTC+3. Плановый забой, скрытая категория, выключенная видимость, нулевой остаток или истёкший срок скрывают позицию в предпросмотре.
- `site-copy` хранит контакты, заголовок, подзаголовок, текст о фабрике, условия покупки и ID фотографии. `production` хранит сведения о происхождении, сертификации, этапах и ингредиентах. Редактор поддерживает переход из заполненного черновика на проверку и подтверждение, после которого сведения можно отметить для публикации. Правка сведений возвращает редактор к черновику. Карточка дат читает тот же график, что каталог.
- `company`, `privacy`, `analytics` и `documents` сохраняются независимо. Реквизиты и правовые тексты редактируются как черновики. Карточка документа содержит ID файла, имя и флаг публикации. Замена файла сбрасывает флаг. Настройки аналитики сохраняются локально и не запускают счётчики или рассылки.
- `retail-stores` хранит адрес, телефон, часы, ссылку на карту, порядок и флаги публикации. Предпросмотр работает с текущим черновиком. Чтобы отметить магазин для публикации, нужны название, адрес, телефон и часы. Самовывоз читается из редактора содержимого и остаётся отдельной точкой.
- Хранилища имеют префикс `karavan.admin.` и суффикс `.v1`. Текст и настройки находятся в localStorage, выбранные фото и документы до 10 МБ — в IndexedDB `karavan.admin.files`. Данные видны в том же профиле браузера и синхронизируются между вкладками. При одновременном редактировании одной записи действует последнее сохранение. Отметки для публикации видны в панели управления. Публичные страницы используют исходные серверные данные. Остатки в публичном каталоге и начальные остатки в панели управления взяты из разных макетов Figma.

## Предлагаемый серверный этап

| Сущность | Поля и связи |
| --- | --- |
| `products` | ID, уникальный slug и артикул, категория, подкатегория, название, описание, фото, фасовка, минимальный объём опта, статус публикации. |
| `categories` | ID, имя, FK родительской категории, позиция сортировки, видимость. |
| `slaughters` | ID, timestamp, часовая зона производства, состояние графика, видимость даты, ручная скидка. |
| `batches` | ID, уникальный slug, FK товара и забоя, остаток, режим хранения, срок годности, базовые цены и минимальные объёмы для розницы и опта, источник скидки, видимость. Уникальная пара товар–забой. Для полуфабриката дата изготовления хранится отдельно от даты забоя сырья. |
| `discount_rules` | ID, уникальный возраст в сутках, процент и активность. Применение рассчитывается по правилам для всего каталога. |
| `content_revisions` | Область редактирования, версия, состояния черновика и публикации, автор и дата. Сведения о производстве, реквизиты, политика и настройки имеют раздельные версии. |
| `media_assets`, `wholesale_documents` | Метаданные файлов и ключи объектов. Документ ссылается на версию файла и хранит тип, область действия, срок, состояние проверки и публикации. |
| `retail_stores` | ID, название, адрес, телефон, часы, ссылка на карту, порядок, видимость в контактах и вывод на главной и в подвале. |
| `wholesale_requests` | ID, уникальный номер, нормализованный телефон, статус, timestamps, ключ идемпотентности. Индекс `(status, created_at)` для админки. |
| `wholesale_request_items` | FK заявки, FK товара, объём в десятичном типе. Уникальная пара заявки и товара. Название и минимум товара снимком на дату заявки сохраняют историю после изменения каталога. |
| `request_consents` | FK заявки, назначение согласия, версия опубликованного текста, момент решения и согласие или отказ. Обязательное согласие и рассылка фиксируются раздельно. |
| `request_status_events` | FK заявки, прежний и новый статус, ID менеджера и время перехода. |

- `POST /api/wholesale-requests` принимает `items: [{ productId, quantityKg }]`, `phone`, `personalConsent`, `marketingConsent` и ключ идемпотентности. Сервер повторно проверяет опубликованные товары, объёмы, телефон и обязательное согласие. Запись заявки, позиций и согласий выполняется одной транзакцией. Версия действующего текста согласия определяется сервером.
- Успешный ответ `201` возвращает публичный номер заявки. `422` содержит ошибки конкретных полей, `429` сообщает об ограничении частоты. Клиент сохраняет текущий черновик при сетевой ошибке. Повтор с тем же ключом и тем же содержимым возвращает результат исходной операции.
- `GET /api/admin/wholesale-requests` обслуживает фильтрацию и пагинацию. `GET /api/admin/wholesale-requests/:id` возвращает карточку. `PATCH /api/admin/wholesale-requests/:id/status` меняет статус, проверяет предыдущую версию записи и пишет событие. Эти маршруты требуют аутентификации менеджера и разграничения доступа.
- Для переноса заменить операции адаптера запросами к API. Тестовые заявки исключить из импорта. Список публичных партий загружать на сервере, сохранив фильтры и URL маршрутов. Ошибки полей, подтверждение и готовность админки проверить повторно по R5–R11.
- Для включения реального приёма заявок предстоит согласовать реквизиты оператора, тексты согласий, срок хранения, получателей уведомлений и роли менеджеров.

### Серверные контракты для админки

| Область | Предлагаемый контракт |
| --- | --- |
| Каталог | `GET /api/admin/catalog/positions` принимает поиск, категорию и ID забоя. `POST /api/admin/catalog/products` создаёт товар и первую позицию транзакционно. `PATCH /api/admin/catalog/positions/:id` принимает изменения партии, при необходимости изменения общих данных товара и версии обеих записей. `DELETE` для позиции и товара имеет разный каскад. |
| Забои | `GET/POST /api/admin/catalog/slaughters`, `PATCH/DELETE /api/admin/catalog/slaughters/:id` и `POST /api/admin/catalog/slaughters/:id/positions`. Забой хранит время в заданной зоне, состояние, дату публикации и ручную скидку. Уникальность пары товар–забой проверяется на уровне БД. |
| Правила и категории | `PUT /api/admin/catalog/discounts` сохраняет режим и ступени вместе. `PUT /api/admin/catalog/categories` сохраняет порядок и видимость. Повторный возраст ступени и удаление категории с зависимостями возвращают `409`. |
| Контент и правовые тексты | `GET/PATCH /api/admin/content/:section` обслуживает раздельные формы. Сведения о производстве хранят версии черновика и опубликованного текста, переход состояния фиксирует редактора и дату. Политика, согласия и настройки аналитики имеют независимые версии. |
| Файлы | `POST /api/admin/uploads` создаёт ID объекта. Сервер проверяет содержимое, размер и права, метаданные хранятся в БД. Публикация документа отдельным действием после проверки. Неиспользуемые и заменённые объекты очищаются с учётом ссылок активных версий. |
| Магазины | `GET/POST /api/admin/stores`, `PATCH/DELETE /api/admin/stores/:id`. Отдельные признаки публикации и вывода на главной и в подвале. Перед публикацией сервер проверяет адрес, телефон, часы и URL карты. |

Изменения принимаются только от авторизованного редактора. Для обновлений полезны версии записей и ответ `409` при конкурирующем изменении. После публикации публичные маршруты читают опубликованные серверные данные и обновляют кэш затронутых страниц.
